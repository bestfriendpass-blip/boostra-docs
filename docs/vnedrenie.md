# Doc-as-Code (MkDocs) vs Confluence: обоснование и руководство по внедрению

Документ состоит из трёх частей:

1. **Сравнение** Doc-as-Code и Confluence — чтобы принять решение.
2. **Организация процесса** — как это работает на уровне компании.
3. **Пошаговая настройка** — чтобы любой сотрудник мог развернуть у себя.

---

# Часть 1. Сравнение Doc-as-Code и Confluence

## Суть различия

- **Confluence** — корпоративная вики: открыл в браузере, пишешь как в Word, все видят. Сильна в широте охвата и низком пороге входа.
- **Doc-as-Code** — «документация как код»: текст в формате Markdown хранится в Git, проходит ревью через Pull Request и публикуется автоматически. Сильна в версионировании, качестве и связи с кодом.

Главный тезис: **это не «что лучше вообще», а «что лучше под конкретную задачу».**

## Таблица сравнения

| Критерий | Doc-as-Code (MkDocs) | Confluence |
|---|---|---|
| Порог входа | Нужны Git, Markdown, редактор ⚠️ | Открыл браузер и пишешь ✅ |
| Визуальный редактор (WYSIWYG) | Нет, пишешь разметку ⚠️ | Да, мышкой ✅ |
| Версионирование | Полная история в Git, привязка к релизу ✅ | История страниц, но не к коду ⚠️ |
| Ревью перед публикацией | Да, Pull Request + обязательные проверки ✅ | Нет реального «гейта» ⚠️ |
| Авто-проверки (орфография, битые ссылки) | Да, в CI ✅ | Нет ⚠️ |
| Связь с кодом | ТЗ лежит рядом с кодом ✅ | Отдельная система ⚠️ |
| Совместное онлайн-редактирование | Через ветки/PR, не одновременно ⚠️ | Да, как Google Docs ✅ |
| Комментарии от нетехнических людей | Только через GitHub ⚠️ | Доступны всем ✅ |
| Аудит «кто/что/когда менял» | Неизменяемая история Git ✅✅ | Есть, но проще обойти ⚠️ |
| Стоимость | Open source, бесплатно ✅ | Лицензия на пользователя 💰 |
| Вендор-локин | Нет (обычный текст) ✅ | Проприетарный формат ⚠️ |

## По трём осям

### 1. Удобство в работе
- Для **технических специалистов** (аналитики, разработчики, кто уже в Git) — Doc-as-Code удобнее: один инструмент, один процесс, пишешь в своём редакторе.
- Для **нетехнических сотрудников** (юристы, менеджмент, комплаенс) — Confluence удобнее: не надо учить Git.
- **Актуальность**: Doc-as-Code выигрывает — ревью и авто-проверки не дают документации «протухнуть» или сломаться. В Confluence со временем накапливаются мёртвые и устаревшие страницы.

### 2. Передача в разработку — самая сильная сторона Doc-as-Code
- ТЗ лежит **в том же репозитории, что и код**, и версионируется вместе с релизом.
- Разработчик видит изменения ТЗ в том же diff/Pull Request, что и код.
- Нет проблемы «ТЗ в Confluence разъехалось с реальным кодом».
- Диаграммы (Mermaid) — тоже код, меняются вместе с текстом, а не отдельными картинками, которые кто-то забыл обновить.

### 3. Удобство для бизнеса
- Если «бизнес» = менеджмент/заказчики, которым **читать и комментировать**, — Confluence привычнее и доступнее.
- Реальные плюсы Doc-as-Code для бизнеса: **дешевле** (нет лицензий), **выше качество и актуальность**, и особенно для МФО — **железный аудит изменений**: неизменяемая история, кто и когда что поправил. Для регуляторной документации прозрачность и доказуемость изменений — серьёзный аргумент.
- Минусы: нужно обучить людей и держать человека, кто поддерживает CI; часть нетехнических сотрудников будет сопротивляться.

## Вывод

**Не «заменить Confluence», а использовать правильный инструмент под задачу:**

- **Техническая документация** (ТЗ, API, архитектура, runbooks, схемы БД) — в **Doc-as-Code** рядом с кодом. Здесь он заметно лучше.
- **Общекорпоративная вики** (встречи, политики, HR) — остаётся в **Confluence**.

Самый жизнеспособный вариант внедрения — **гибрид**, а не «всё переносим». Это снижает сопротивление и риск. Существуют интеграции «публикация Markdown → Confluence»: исходник живёт в Git с ревью, а бизнес читает привычную витрину в Confluence.

# Часть 2. Как это организовать в компании

## Что где хранится

| Тип документа | Где |
|---|---|
| ТЗ, API, архитектура, схемы БД, runbooks | Doc-as-Code (Git + MkDocs) |
| Протоколы встреч, политики, HR, общие вики-страницы | Confluence |

## Роли в процессе

- **Автор** — пишет/правит документацию в Markdown, открывает Pull Request.
- **Ревьюер** — читает изменения, комментирует по строкам, одобряет.
- **Мейнтейнер портала** — следит за CI, структурой, настройками (1 человек на команду).

## Жизненный цикл документа

```
Автор создаёт ветку
        │
        ▼
Правит .md, смотрит локально (mkdocs serve)
        │
        ▼
Коммит + push + Pull Request
        │
        ▼
Авто-проверки: орфография + сборка + битые ссылки
        │
        ▼
Ревьюер смотрит и одобряет
        │
        ▼
Merge в main
        │
        ▼
Авто-деплой → сайт обновился (GitHub Pages)
```

## Правила и соглашения (рекомендуемые)

- **Прямой push в `main` запрещён** — только через Pull Request (настраивается защитой ветки).
- **Обязательные проверки** перед merge: орфография (`spellcheck`) и сборка (`build`).
- **Именование веток**: `docs/<короткое-описание>` (например `docs/api-platezhi`).
- **Один PR — одно логическое изменение**: так проще ревьюить.
- **Словарь терминов** компании ведётся в `.cspell/project-words.txt` — туда добавляются «не-опечатки» (названия систем, термины).
- **Структура репозитория**:
  ```
  docs/           — страницы документации (.md)
  docs/includes/  — служебные включения (глоссарий)
  overrides/      — кастомизация темы
  mkdocs.yml      — конфигурация портала и навигация
  .github/workflows/ — авто-проверки и авто-деплой
  ```

## Что нужно от компании

- **Репозиторий** на GitHub (или GitLab/самохост) — один на портал документации.
- **Права доступа**: команда — на запись через PR; мейнтейнер — админ.
- **Площадка публикации**: GitHub Pages (приватный сайт — платный план; публичный — бесплатно) или внутренний хостинг статики.
- **Обучение**: 1–2 часа на сотрудника по этому руководству.
- **Поддержка**: мейнтейнер, который отвечает за CI и структуру.

## Как это работает на компанию (итог)

1. Портал настраивается **один раз** мейнтейнером.
2. Каждый сотрудник **единожды** ставит инструменты у себя (Часть 3).
3. Дальше любой правит документацию, открывает PR, проходит авто-проверки и ревью.
4. После merge сайт обновляется сам — у всех всегда актуальная версия по одной ссылке.

# Часть 3. Пошаговая настройка для сотрудника (Windows)

> Это ровно тот путь, который проверен на практике, со всеми граблями и обходами.
> Делается **один раз**. Дальше — только работа через Pull Request.

## Предварительно

- Аккаунт на **GitHub** (если нет — зарегистрироваться на github.com).
- Доступ (приглашение) в **репозиторий документации** компании.

## Шаг 1. Установить Python

Скачать с [python.org](https://www.python.org/downloads/) и при установке **поставить галочку «Add Python to PATH»**.
Проверка в терминале:
```
python --version
```

## Шаг 2. Установить MkDocs и плагины

```
pip install mkdocs mkdocs-material mike mkdocs-print-site-plugin
```
Проверка:
```
mkdocs --version
```

## Шаг 3. Установить редактор и расширения

- Редактор: **VS Code** или **Cursor**.
- Расширения (панель Extensions, `Ctrl+Shift+X`):
  - **Markdown Preview Mermaid Support** — чтобы диаграммы рисовались в предпросмотре.
  - **GitHub Pull Requests** — работа с PR внутри редактора (по возможности).
  - (в репозитории эти расширения уже рекомендованы через `.vscode/extensions.json` — редактор предложит их сам).

## Шаг 4. Получить проект

Клонировать репозиторий документации компании:
```
git clone https://github.com/КОМПАНИЯ/РЕПОЗИТОРИЙ.git
```
Открыть папку в редакторе (File → Open Folder).

## Шаг 5. Локальный предпросмотр

В терминале редактора, находясь в папке проекта:
```
mkdocs serve
```
Команда напечатает адрес вида `Serving on http://127.0.0.1:8000/` — открыть его в браузере.
Правишь `.md`, сохраняешь (`Ctrl+S`) — сайт обновляется сам.

**Предпросмотр «документ слева — результат справа» в редакторе:**
открыть `.md` → `Ctrl+K`, затем `V`. С расширением Mermaid там же рисуются диаграммы.
(Полный вид со всеми фишками MkDocs — только в браузере через `mkdocs serve`.)

## Шаг 6. Установить GitHub CLI и войти

Установка:
```
winget install --id GitHub.cli -e
```
После установки **перезапустить терминал** (а лучше весь редактор), чтобы команда `gh` стала видна.

Вход:
```
gh auth login
```
Выбрать: `GitHub.com` → `HTTPS` → `Yes` → `Login with a web browser`.

### ⚠️ Если вход через браузер не проходит (таймаут / «connection closed»)

В некоторых сетях эндпоинт входа через браузер режется. Обход — **вход по токену**:

1. Создать токен: открыть
   `https://github.com/settings/tokens/new?scopes=repo,read:org,workflow`
   — отметить scopes **`repo`**, **`read:org`**, **`workflow`** → Generate token → скопировать `ghp_...`.
2. Войти токеном (PowerShell):
   ```
   "ghp_ВАШ_ТОКЕН" | gh auth login --with-token
   ```
3. Проверить:
   ```
   gh auth status
   ```

Настроить git на работу через gh (один раз):
```
gh auth setup-git
```

## Шаг 7. Рабочий цикл — внесение правки через Pull Request

```
# 1. Новая ветка от main
git checkout main
git pull
git checkout -b docs/moya-pravka

# 2. (правишь .md в редакторе, смотришь через mkdocs serve)

# 3. Зафиксировать
git add .
git commit -m "Коротко: что поменял"

# 4. Запушить ветку
git push -u origin docs/moya-pravka

# 5. Открыть Pull Request
gh pr create --fill

# 6. Посмотреть статус проверок
gh pr checks

# 7. После зелёных проверок и одобрения — смержить
gh pr merge --squash --delete-branch
```

То же самое кнопками в редакторе: ветка и коммит — в панели **Source Control** (`Ctrl+Shift+G`), PR — в панели **GitHub Pull Requests**.
Либо всё через сайт github.com (кнопки «Compare & pull request» и «Merge»).

После merge сайт пересобирается и обновляется **автоматически** за ~30 секунд.

## Шаг 8. Как добавить новую страницу

1. Создать файл, например `docs/razdel/statya.md`.
2. Прописать его в навигации в `mkdocs.yml`:
   ```yaml
   nav:
     - Раздел:
         - Статья: razdel/statya.md
   ```
3. Проверить локально (`mkdocs serve`) и отправить через Pull Request (Шаг 7).

## Шаг 9. Как устроена публикация (для понимания)

- При merge в `main` запускается GitHub Actions (`.github/workflows/ci.yml`), который собирает сайт и публикует его (через `mike`) на GitHub Pages.
- Отдельный workflow (`.github/workflows/checks.yml`) на каждый PR проверяет орфографию и сборку.
- Ничего публиковать руками не нужно — всё делает CI.

## Шаг 10. Проверки против устаревания (maintenance)

Помимо обязательных проверок на PR (`build`, `spellcheck`), в портале настроены вспомогательные проверки обслуживания (`.github/workflows/maintenance.yml`). Они запускаются на PR и **по расписанию** (раз в неделю):

- **Проверка внешних ссылок** (`lychee`) — находит «мёртвые» внешние ссылки, которые ломаются со временем. Настройка исключений — в `lychee.toml`. По умолчанию проверка в режиме отчёта (не блокирует merge); чтобы сделать её блокирующей, в workflow поставить `fail: true`.
- **Проверка дат пересмотра** (`scripts/check_freshness.py`) — смотрит поле `last_reviewed` в начале каждой страницы и подсвечивает те, что не пересматривались дольше порога (по умолчанию 180 дней) или вовсе без даты. Это сигнал «страницу пора перечитать», а не ошибка.

Чтобы отметить страницу как пересмотренную, добавь в самое начало файла:

```yaml
---
last_reviewed: 2026-10-01
---
```

> Важно: автоматика ловит «сломалось» (битые ссылки/структура) железно, а «устарело по смыслу» — делает заметным (просроченные даты, мёртвые ссылки), но не читает смысл. Финальную актуальность подтверждает человек при пересмотре.

## Шаг 11. Бот-напоминание про обновление документации

Отдельный workflow (`.github/workflows/docs-reminder.yml`) помогает против рассинхрона кода и документации. На каждом Pull Request он сравнивает: менялся ли код/настройки и трогали ли папку `docs/`.

- Если **код меняли, а документацию — нет**, бот оставляет в PR комментарий: сообщить системному аналитику, чтобы он актуализировал ТЗ/документацию под внесённые изменения.
- Комментарий один и обновляется (не спамит), merge **не блокирует** — это подсказка человеку.

Что считать «кодом», задаётся прямо в workflow (строка с перечнем папок). В реальном проекте туда вписывают свои папки кода, например `src/`, `api/`, `backend/`, `frontend/`:

```yaml
code="$(echo "$changed" | grep -E '^(src/|app/|backend/|frontend/)' || true)"
```

> Зачем это нужно: самый частый источник устаревания — разработчик по дороге добавил своё или бизнес попросил изменить, а ТЗ осталось старым. Бот ловит ровно этот случай и напоминает в момент изменения, а не через полгода. Смысл он не проверяет — решение всегда за человеком (автором и ревьюером).

## Приложение. Типовые проблемы и решения

| Проблема | Причина | Решение |
|---|---|---|
| `&&` не работает в терминале | Это Windows PowerShell, а не Bash | Разделять команды `;` или запускать по одной |
| `gh : имя не распознано` | PATH не обновился после установки | Перезапустить редактор полностью; или запускать по полному пути `& "C:\Program Files\GitHub CLI\gh.exe" ...` |
| `gh auth login` виснет/timeout | Провайдер режет OAuth-вход | Вход по токену (Шаг 6, обход) |
| `missing required scope 'read:org'` | У токена не хватает прав | Пересоздать токен со scopes `repo, read:org, workflow` |
| Порт 8000 занят | Уже запущен другой `mkdocs serve` | Остановить старый (`Ctrl+C`) или запустить на другом порту: `mkdocs serve -a 127.0.0.1:8001` |
| В адресе появляется лишний `/REPO/` | Задан `site_url` с под-путём | Для локальной работы это норма; важно для публикации на GitHub Pages |
| Диаграммы не рисуются в предпросмотре редактора | Нет расширения | Поставить «Markdown Preview Mermaid Support» |
